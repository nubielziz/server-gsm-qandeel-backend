# P2.3 data

Phase 2, feature 3. Read `_common.md` first. Work in the worktree path given in your prompt (a checkout of branch
`feat/backend-p2-data`, already containing P2.1). Decisions: 005 (pg driver), 010 (ids, tokens), 011 (money types),
019 (encrypted and hashed columns), 024 (ledger), 025 (order states), 027 (database conventions, the core of this
brief). Backend schema additions: `docs/contract/MISMATCHES.md` (the "schema" row and each B-entry it cites).
Table ownership: `scripts/module-map.mjs`. Table columns and English descriptions: `docs/slices/<module>.json`
(`ownedTables`).

## Build

1. **Schema** for all 66 tables plus the additions, one file per module `src/modules/<id>/db/schema.ts` (only the
   module's own tables), re-exported by `src/infra/db/schema.ts`; `drizzle.config.ts` at the root (schema = that
   file, out = `drizzle/`, `casing: 'snake_case'`, credentials from `DATABASE_URL`). You may scaffold the files once
   from the slices with a throwaway script, then refine them by hand: the committed schema files are the source of
   truth, not a generator.
   - Types, nullability, ids, timestamps, money/rate precision, booleans, jsonb, arrays, external ids: decision 027.
   - Enumerations (status, kind, type, purpose, channel, scope, source, method…): `text` + `CHECK (col IN (…))`, the
     values exported from one `as const` array per enum next to the table. Sources, in order: the frontend wire enums
     for that field (query `docs/contract/frontend-endpoints.json`), decisions 018/024/025 (session stages, ledger
     kinds and ref types, order status and dispatch states), the map scenarios' state chains (slices `scenarios`),
     `docs/contract/endpoints/<module>.md`. A column whose values no source fixes stays plain `text` and goes into your
     report.
   - Constraints the map and decisions imply: unique keys (lower-cased emails, usernames, `token_hash`, `key_hash`,
     `idempotency_key`, `public_token`, `checkout_sessions.token`, ledger account identity `(kind, owner_type,
     owner_id, currency)`), `orders` one-of check (`client_id` xor `customer_id`), positive amounts where the meaning
     requires it, `ledger_entries.amount <> 0`; an index on every foreign key and on every list filter/sort column of
     the module's endpoints; partial indexes for hot states (open orders, unprocessed outbox rows, active sessions).
   - Encrypted columns (`*_enc`) are `text` holding the decision-019 format; hashed columns are `text` (hex).
   - Each table has TSDoc: the English description (slices) and a Why line; non-obvious columns get a short comment.
     Every exported symbol (tables, enum arrays, inferred row types) has TSDoc: the parallel P2.2 adds a lint rule
     that enforces it.
   - Cross-module foreign keys: a module's `db/schema.ts` may import another module's `db/schema.ts` directly (the
     only exception to the `index.ts` rule besides `src/infra/db/schema.ts`; P2.2's boundary lint encodes both).
2. **Migrations**: `drizzle-kit generate` produces the first migration; a custom migration (`drizzle-kit generate
   --custom`) adds the SQL Drizzle cannot express: the deferred zero-sum constraint trigger on `ledger_entries`, the
   append-only triggers on `ledger_entries`, `ledger_transactions`, `order_events` and `audit_logs` (raise on UPDATE
   or DELETE), and anything else your constraints need. Scripts `db:generate`, `db:migrate` (drizzle-orm migrator,
   never on app boot), `db:check` (no pending schema change).
3. **DB runtime** (`src/infra/db/`): a `DbModule` providing the Drizzle instance (pg `Pool`, size from config,
   `casing: 'snake_case'`, the schema) and a transaction helper `runInTransaction(fn, { isolation? })` whose
   callback gets `tx` plus `afterCommit(cb)` (callbacks run only after a successful commit; used for cache
   invalidation, decision 022). Pool closed in `onApplicationShutdown`. A Postgres health indicator (`postgres`,
   critical) is registered with `HealthRegistry` from `src/infra/health` (import `HealthRegistryModule`; never import
   `src/modules/health`: `src/infra` must not import domain modules).
4. **Tests support**: the test preload migrates `gsm_test` once per run (`DATABASE_URL_TEST`); `resetDb()` truncates
   every table except the migrations table (`TRUNCATE … RESTART IDENTITY CASCADE`). Integration tests: the migration
   applies on an empty database; the zero-sum trigger rejects an unbalanced transaction at commit and accepts a
   balanced one; UPDATE/DELETE on the append-only tables raises; the orders one-of check; a unique email is
   case-insensitive; `afterCommit` runs after commit and not after rollback; `db:check` reports no drift.
5. **Seed framework** `bun run db:seed` (`scripts/seed/`, development only, refuses `NODE_ENV=production`): loads the
   frontend demo state (`$FRONTEND_DIR/src/mocks/seed/demo-state.json`, read-only) and maps it to rows with the same
   id rule as the frontend mocks (demo id `'m3'` → 3, `'ad1'` → 1: find the rule in the frontend's
   `src/mocks/seed/index.ts` and the feature mocks), timestamps rebased to now, money as 4-decimal values. One seeder
   file per module; each Phase 3 feature adds its module's seeder. In this feature seed: the system ledger accounts
   (decision 024, incl. `owner_capital`), the 6 roles with the exact permission lists of the frontend mocks
   (`docs/contract/extraction/auth-access.json` → `permissions`), the 6 staff members (ids, names, emails, roles,
   statuses as in the mocks; password hashes left null for now: P2.6 sets the dev credentials), the IP rules and the
   access restriction setting. Idempotent: running it twice gives the same database.

## Out of scope
Repositories and services of the modules (Phase 3), Redis, guards, sign-in.

## Done when
`bun run db:migrate` applies cleanly on an empty `gsm` and `gsm_test`; `bun run db:check` shows no drift;
`bun run typecheck` and `bun test` are green; `bun run db:seed` runs twice without error. Report the enum columns you
left as plain text and every column whose type you had to guess.
