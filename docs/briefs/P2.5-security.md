# P2.5 security

Phase 2, feature 5. Read `_common.md` first. Work in the worktree path given in your prompt (branch
`feat/backend-p2-security`, containing P2.1–P2.4). Decisions: 018 (auth, sessions, CSRF, pipeline: the core of this
brief), 019 (token hashing), 021 (rate limits), 022 (cache), 028 (errors). Contract: `docs/contract/ALIGNMENT.md`
§§ 3–6; session-ending codes rule; permissions grammar; the B-entries on Owner guards. Seed data from P2.3 (roles,
staff, IP rules, restriction setting) is available for tests.

Placement (module boundaries): sessions, API keys, IP rules, permissions and the auth guards live in the identity
module (`src/modules/identity/security/`, exported from its `index.ts`); the maintenance hook and the audit service
live in the platform module (it owns `settings` and `audit_logs`); the per-IP limiter hook lives in
`src/infra/rate-limit/`. `src/common` and `src/infra` never import modules: modules register their hooks on the
Fastify instance (via `HttpAdapterHost`) in the pipeline order of decision 018.

## Build

1. **IP rules hook** (identity): active `ip_rules` cached in the cache Redis (a `CacheKeys` builder, invalidated on any
   change through `afterCommit`), matched against the real client IP (`request.ip` with `TRUST_PROXY`): block rules
   first (scopes per the seed and the endpoints doc), then, for `/admin/*` when the access restriction setting is on,
   the allowlist. Refusal: `403 IP_NOT_ALLOWED` (problem+json; CORS headers present). Hit counters increment in Redis
   and a worker scheduler flushes them to `hit_count`/`last_hit_at` every minute (register it with the P2.4 registry).
2. **Maintenance hook** (platform): maintenance settings (enabled + scopes + message) cached; scoped surfaces answer
   `503 MAINTENANCE` (Dhru envelope on `/api/index.php` through the P2.1 seam); `/admin/*`, `/health`, `/metrics` never.
3. **Per-IP rate limit hook** on the public surfaces (store, auth routes, token routes) with limits from config.
4. **Session service** (identity): create (subject type, subject id, stage, ttl, ip, user agent), rotate (new token,
   old revoked), touch (`last_seen_at` at most once a minute), revoke (one, or all of a subject), lookup by token hash
   with a 60 s cache (deleted on revoke); absolute and idle expiry from settings (staff 8 h / 30 min, merchants and
   customers 30 d / 7 d, pending stages 10 min); cookie helpers (names per subject, httpOnly, Secure from
   `COOKIE_SECURE`, SameSite=Lax, Path=/, `__Host-` prefix when secure) and the CSRF token (HMAC of the session
   token hash with `CSRF_SECRET`; readable `csrf_token` cookie with `CSRF_COOKIE_DOMAIN`; `X-CSRF-Token` header).
5. **Guards**, chosen from the contract's `access`:
   - staff session / staff permission (admin): active stage only (pending → 401 except the routes that declare the
     pending stage they accept), staff status active (suspended → revoke all its sessions, `403
     ACCOUNT_SUSPENDED`), principal with the role's current permissions (cached per role, invalidated on role change).
   - merchant session (client) and customer session (store): the same mechanics with their tables and statuses.
   - capability tokens (checkout, tracking, ticket, link tokens): the guard extracts the token and calls a resolver
     the owning module registers later (P2.5 provides the registry and a test resolver).
   - API key (v1): `Authorization: Bearer <key>` → hash lookup → revoked/expired/allowed IPs (CIDR)/scope ⊇ the
     contract's permission/per-key limit/merchant status; principal with client id, key id and scopes.
   - Dhru credentials: `username` + `apiaccesskey` from the form body → the same checks with scope `dhru`; failures
     use the Dhru envelope (`Authentication Failed`) instead of problem+json.
   - Webhook signatures: a verifier registry per gateway (adapters come with billing); P2.5 provides the registry,
     the timestamp window and event-id de-duplication (cache Redis), and a test adapter.
6. **CSRF guard**: every cookie-authenticated mutation needs `X-CSRF-Token` equal to the session's token
   (constant-time) → else `403 CSRF_FAILED` (does not sign out); session-less mutations on `/admin` and `/client`
   need an `Origin` in `CORS_ORIGINS`.
7. **Permission guard**: grammar of decision 018 (`x:*`, `*`, required `x:*` needs `x:*` or `*`), `403 FORBIDDEN`
   whose detail names the missing permission; `PermissionsCatalog.list()` = every concrete permission used by the
   registered contracts (sorted, unique), for `GET /admin/permissions` later; an `isOwner(principal)` helper (role
   contains `*`) and `assertOwnerTargetAllowed(caller, target)` (actions on an Owner need `*`).
8. **Audit** (platform): `AuditService.record(tx, { action, entityType, entityId, entityLabel, before, after })`
   called by services inside their transaction (actor and ip from the request context); a request-level check marks
   every staff-authenticated non-GET route whose contract does not say `audit: false` and, in development and tests,
   fails the request (500 with a clear log) when no audit record was written; in production it logs an error.
9. **Docs gate**: implement `REFERENCE_DOCS_GUARD` (staff session with `system:read`) so `REFERENCE_DOCS=staff` works.
10. **Tests** (integration, real Postgres and Redis): pipeline order (blocked IP → 403 before auth, with CORS
    headers; maintenance 503 on store, not on admin), each guard's accept and refuse cases, expiry (absolute, idle,
    pending stage), suspended staff → 403 ACCOUNT_SUSPENDED and sessions revoked, CSRF missing/mismatch/ok, Origin
    check, permission wildcards and the required-`x:*` rule, API key revoked/expired/wrong IP/missing scope/limit 429
    with `Retry-After`, Dhru auth failure envelope, webhook signature window and replay, audit enforcement.

## Out of scope
The sign-in endpoints (P2.6), staff/roles/IP-rule CRUD routes (feature 2a), gateway adapters (billing).
