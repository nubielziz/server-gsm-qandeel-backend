# P2.6 staff-sign-in

Phase 2, feature 6. Read `_common.md` first. Work in the worktree path given in your prompt (branch
`feat/backend-p2-signin`, containing P2.1–P2.5). Routes (identity module, stage 2): `POST /admin/auth/login`,
`POST /admin/auth/2fa`, `POST /admin/auth/2fa/setup`, `POST /admin/auth/logout`, `POST /admin/auth/password/set`,
`GET /admin/auth/me`. Contract: `docs/contract/ALIGNMENT.md` § 3 (the exact flow), `docs/contract/endpoints/identity.md`
(these six sections: shapes, errors, B1–B3), `docs/contract/frontend-endpoints.json` (exact request/response shapes),
`docs/contract/RULES.md` § auth. Decisions 007, 018, 019, 021. The session, CSRF and guard machinery comes from P2.5.

## Build

1. The six routes as zod contracts matching the frontend shapes exactly (contract tests from P2.7 will compare them),
   in `src/modules/identity/` (contracts, controller, application service, repository); remove them from
   `test/contract/pending.ts`.
2. Login order: IP rules (pipeline) → rate limit (email + IP; `429` with `Retry-After`) → credentials (`401
   UNAUTHORIZED`, the same answer and similar timing for unknown email, wrong password and no password yet: hash a
   dummy password when the email is unknown) → suspended (`403 ACCOUNT_SUSPENDED`) → pending session (10 min) and
   `{ next }` (`password` first when `must_change_password`, then `totp` when 2FA is on, else `totp_setup`); set the
   session cookie, the CSRF cookie and `X-CSRF-Token`.
3. TOTP (otplib, 6 digits, 30 s, ±1 step): `2fa/setup` stores a new pending secret encrypted (decision 019) and answers
   `{ secret, otpauthUrl, qrSvg }` (SVG via the `qrcode` package); refuses when 2FA is already on (`409
   TWOFA_ALREADY_ENABLED`). `2fa` verifies the code (a used time step is never accepted twice: remember the last step
   per staff member), confirms a pending secret (`twofa_enabled = true`), rotates the session to `active`, sets
   `last_login_at`/`last_login_ip`, turns `invited` into `active`, sends `X-CSRF-Token`; wrong code → `422
   VALIDATION_FAILED` on `code`; attempts rate-limited per session.
4. `password/set`: token mode `{ token, password }` (an `auth_tokens` row by hash, purpose staff invite or reset, unused,
   not expired; else `410 TOKEN_INVALID`); session mode `{ password }` only on a `pending_password` session. Password
   policy: ≥ 10 characters and not trivially weak (`422 WEAK_PASSWORD` on `password`); argon2id hash; clears
   `must_change_password`, sets `password_changed_at`, marks the token used, revokes the subject's sessions; `204`; no
   sign-in. Provide a small internal service to create invite/reset tokens (used by staff management in feature 2a and
   by tests).
5. `logout`: revoke, clear both cookies, `204`. `me`: the Me shape, `401` until active, `Cache-Control: no-store`,
   `X-CSRF-Token` on the response.
6. Audit: successful sign-in, sign-out and password set are audit entries if the frontend's audit screen expects them
   (check `RULES.md` § audit and the audit endpoints doc); failed attempts are logged and rate-limited, not audited.
7. Dev credentials: the seed (P2.3) gets password `demo-password` (argon2id) for the seeded active staff in
   development and a fixed, documented TOTP secret per seeded staff member (README "Local sign-in"), so the console
   can sign in against the real API with any authenticator; no code path skips TOTP.
8. Tests: the frontend flow end to end through HTTP (`inject`): login → setup → 2fa → me → logout; temporary password
   (`next: password`) → password/set → login again; invite token → set → login; each error code of the six sections
   (401 cases, 403 suspended, 403 IP, 410, 422 weak/code, 409 2FA on, 403 CSRF, 429); replayed TOTP step refused;
   pending session cannot call `me`; session rotation on 2FA (old token dead).

## Done when
`bun run check` is green (contract tests compare these six routes); the console's sign-in works against
`bun src/main.ts` with the seeded staff (verify with `curl` through the whole flow, computing the TOTP code from the
documented secret).
