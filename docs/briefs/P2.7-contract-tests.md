# P2.7 contract-tests

Phase 2, feature 7. Read `_common.md` first. Work in the worktree path given in your prompt (branch
`feat/backend-p2-contract`). Design: `docs/contract/TESTS.md` (read it fully). Decisions: 008, 009, 028. Inputs:
`docs/route-manifest.json`, `docs/contract/frontend-endpoints.json`, `docs/contract/error-codes.md`,
`docs/contract/MISMATCHES.md` (B-ids), `docs/contract/ALIGNMENT.md` § 8 (fixture harvest recipe, verified).

## Build

1. **Comparator** `test/contract/lib/compare.ts`: compares a frontend shape (the JSON shape format of
   `frontend-endpoints.json`: `type`, `const`, `enum`, `array`, `object`/`optional`, `record`, `anyOf`, `nullable`,
   `alias`) with a backend JSON Schema (zod → JSON Schema 2020-12, `x-gsm-alias` markers) for responses and requests,
   with the rules of TESTS.md § 2. Every difference is reported with a path (`data[].status`) and a rule name. Unit
   tests with small hand-made shapes cover each rule (required, types, aliases, enums subset, nullability, arrays,
   records, `ListResult<T>` ↔ array + `x-total-count`, success status, extra backend fields reported not failing).
2. **Tests** in `test/contract/` run by `bun test`:
   - `route-parity.test.ts`: registry keys = manifest `kind: http` keys minus `pending.ts`; every pending key is in
     the manifest and not in the registry (a built route must leave `pending.ts`); Fastify serves exactly the
     registry's routes plus the documentation routes (`/reference`, `/reference/openapi.json`); Dhru actions,
     supplier calls and event schemas = manifest `DHRU`/`SUPPLIER`/`EVENT` keys minus pending (registries may still
     be empty); every `frontend-endpoints.json` key is built or pending.
   - `shape-parity.test.ts`: for each built route that the frontend calls: response, request and success status
     compared with the comparator; each harvested fixture validates against the backend response schema (ajv, draft
     2020-12, formats); deviations pass only through `test/contract/allowlist.ts` entries `{ route, path, rule,
     mismatch: 'B<n>', reason }` (an entry whose B-id is not in MISMATCHES.md fails; an entry that no longer matches
     anything fails, so the list cannot rot).
   - `error-parity.test.ts`: the error catalog = `docs/contract/error-codes.md` (code, status); every code the
     frontend references (codes marked "Frontend" there, and codes in `frontend-endpoints.json` consumers recorded
     by the extraction) exists with the same status; prints backend-only codes as a report.
   - `openapi-examples.test.ts`: every example in `docs/contract/openapi.json` validates against its schema.
3. **pending.ts**: generated once by `scripts/gen-contract-pending.mjs` from the manifest minus the registry (keys
   grouped by module with a comment per group); afterwards maintained by the features that build routes.
4. **Fixture harvest** (`test/contract/harvest/`): the vitest config and test of ALIGNMENT § 8 (config outside the
   frontend, caches here, run with the frontend's Vitest under Node), signing in with the demo credentials and
   calling every GET route of the console once with representative ids and filters (from the seed ids), plus the
   mutations that answer a body (bodies taken from the frontend's own tests or mocks). Writes
   `test/contract/fixtures/frontend/<METHOD>_<path-slug>.json` = `{ status, headers, body }`. Script
   `contract:harvest` (node, frontend Vitest binary); the fixtures are committed so `bun test` never needs the
   frontend's dependencies. Normalise nothing at write time; the test compares shapes and formats, not values.
5. Add the contract tests to `bun run check` (they are part of `bun test`) and describe the workflow in
   `test/contract/README.md` (what each test proves, how to add an allowlist entry, how to re-harvest).

## Done when
`bun test test/contract` is green with the routes built so far (the few P2.x routes are compared, everything else is
pending); the harvest produced fixtures for every console GET route; the comparator's unit tests cover every rule.
