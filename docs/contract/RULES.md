# Business rules the frontend relies on

Generated by `scripts/build-contract-docs.mjs`; edit `docs/contract/lead-decisions.json` or the extraction, not this file.

Rules the server must enforce (the console only hints them), per frontend feature, with their sources; then the
frontend's own mismatch entries that change what the backend does. Module briefs cite the features they cover.

## auth

Four public screens (/login, /login/2fa, /login/setup-2fa, /set-password) run a two-step staff sign-in through Refine's authProvider (src/app/providers/authProvider.ts). GET /admin/auth/me then feeds identity, every permission gate and 'your address' (lastLoginIp). Logout ends the server session; invite/reset links and the forced change of a temporary password both go through POST /admin/auth/password/set.

1. 2FA is mandatory: no full session without a TOTP code (staff_users description; admin surface "staff session + 2FA + permission").
2. IP rules run before the password on login and before authentication on every /admin route: active block (scope admin|all) or restriction on + IP not allowlisted → 403 IP_NOT_ALLOWED, and the deciding rule gets hit_count+1 / last_hit_at (map ip-rules step 3; backend decision 028).
3. A suspended account is refused with 403 ACCOUNT_SUSPENDED even with the right password, and none of its old sessions work (map admin-team step 8).
4. Pre-2FA session scope: only POST /admin/auth/2fa, /2fa/setup (2FA off), /password/set without token (must_change_password) and /logout accept it; every other route answers 401 (mock requireSession stages, session.ts:103-121). Short lifetime (proposed 10 min).
5. next order at login: must_change_password → password; else twofa_enabled → totp; else totp_setup (session.ts:216).
6. Without a token, POST /admin/auth/password/set is allowed only for a pre-2FA session whose staff member has must_change_password=true; otherwise a stolen password alone could change the password without the TOTP step (the mock only checks the pre-2FA stage, session.ts:287-291).
7. last_login_at and last_login_ip are written at 2FA completion from the request (map admin-team step 5); the console uses lastLoginIp as the caller's address.
8. status 'invited' becomes 'active' at the first full sign-in (staff_users description).
9. Invite/reset tokens are stored as hashes, valid 1 h, single use (auth_tokens description); setting a password consumes the token and ends all sessions of the account.
10. A temporary password forces a change before anything else (next=password); passwords and TOTP secrets never appear in later responses, logs or audit entries (POST /admin/staff/:id/password description).
11. Rate limits with Retry-After on login, 2fa, 2fa/setup and password/set (backend decision 021).
12. CSRF: every mutation that carries a session needs a matching X-CSRF-Token (decision 006); login and token-mode password/set have no session to bind to (rely on SameSite cookies + Origin check).

Frontend mismatches with backend impact:

- **M5** The demo has no sign-in, 2FA or set-password screens; they were built from the map in the demo style. Backend: The backend contract for sign-in is decision 006 as implemented here: login → {next} → 2fa | 2fa/setup + 2fa | password/set → me.
- **M6** The map names the auth routes but not their bodies (next step, QR format, me fields, CSRF token source). Backend: All auth bodies are assumptions isolated in features/auth/api and lib/api/csrf.ts; implement these exact shapes or the console needs a change.

## access

"Admins and access" (/access): five tabs gated by staff:read (Admins), access:read (Allowed IPs, Blocked IPs + tester), roles:read (Roles) and sessions:read (Sessions); any one opens the page (M19). Short lists are loaded whole (staff and roles up to 200, IP rules up to 500 per kind) and sorted, filtered and counted client-side; sessions page by 25. Actions run in dialogs that show the server's problem detail or field errors; client guards (yourself, last Owner, /16, self-lockout) are hints only and the server must enforce them.

1. Cannot suspend yourself; the last active Owner cannot be suspended (manifest POST /admin/staff/:id/suspend; map admin-team step 7; mock accessStaff.ts:196-215).
2. Cannot change your own role; the last active Owner cannot be demoted (map admin-team step 6; demo updateAdmin 14-state-access.js:61-62).
3. Suspension ends every session at once and keeps the record and audit history; reactivation restores sign-in with the existing password and 2FA, status active if the account ever signed in else invited (admin-team steps 7 and 9; mock accessStaff.ts:225-232).
4. Staff email is unique (case-insensitive): 409 EMAIL_TAKEN on create and edit (admin-team step 1; mock accessStaff.ts:96-98).
5. Adding staff needs staff:create; the invite token is a hash, 1 h, single use; a temporary password is generated by the server, hashed, returned once, and forces a change at first sign-in (admin-team steps 1-3; M12).
6. Passwords are never readable and never written to the audit log; only the fact of a change is logged (manifest POST /admin/staff/:id/password).
7. Reset 2FA clears the secret and ends the target's sessions except the caller's own; the next sign-in enrols a new authenticator (admin-team step 9; mock accessStaff.ts:234-238).
8. IP rules: block beats allow; allow rules are only for the admin console (scope admin); a rule may expire (expires_at) and then drops out by itself; active rules are cached in Redis and invalidated on every change (ip_rules description; ip-rules steps 3-4).
9. A range wider than /16 and a duplicate live rule are refused (ip-rules step 1).
10. Turning the console restriction on is refused when the requester's IP is outside the allow list; the switch lives in settings (manifest PUT /admin/access/restriction; ip-rules step 2).
11. A block whose scope is admin or all and that covers the caller's own IP is refused (ip-rules step 5).
12. Removing the only live allow rule that admits the caller while the restriction is on is refused (ip-rules step 9).
13. POST /admin/ip-rules/check is read-only and decides block → allowlist (admin scope with the restriction on) → open (ip-rules step 8; demo ipVerdict).
14. hit_count/last_hit_at grow on the rule that decided a real request (ip-rules step 3); the risk engine adds source=auto block rules (ip-rules step 7).
15. All lockout guards use the real request IP (behind a trusted proxy), not me.lastLoginIp (M15).
16. A role still held by any staff member cannot be deleted (mock ROLE_IN_USE, accessRoles.ts:61-69); role edits apply immediately to every holder (RoleDialog copy).
17. Staff accounts are never deleted (no DELETE route: suspend instead; access/api/resources.ts).
18. Every change to staff, IP rules, the restriction, roles and sessions writes audit_logs (manifest tables of each row).
19. GET /admin/settings must expose adminAllowlistOnly (boolean); PATCH /admin/settings must not change it, because only PUT /admin/access/restriction applies the lockout guard (settings LINKED_SETTINGS, src/features/settings/lib/system.ts:35-43).
20. Permissions: staff:read (list/show), staff:create, staff:update (edit, password, sessions/revoke, reset-2fa), staff:suspend (suspend, reactivate), access:read (rules, check), access:create, access:delete, access:update (restriction), roles:read (+ permissions), roles:create/update/delete, sessions:read, sessions:revoke (manifest + M7).

Frontend mismatches with backend impact:

- **M7** CRUD rows carry x:*; the console reads them as x:read (list/show), x:create, x:update, x:delete; granted x:* matches all. Backend: Server maps each CRUD operation to the concrete permission and matches granted x:* / * the same way.

- **M13** IP verdicts moved from the browser to POST /admin/ip-rules/check. Backend: Implement the verdict order exactly; the console keeps only shape, width and own-address hints.
- **M14** The restriction state is read from GET /admin/settings key adminAllowlistOnly (needs settings:read). Backend: Expose adminAllowlistOnly in GET /admin/settings; PUT /admin/access/restriction writes it.

## audit

Audit log page (/audit, audit:read): a server-paged list, newest first, 25 entries per page, where "Show more" appends the next page; filters for person or system, record type, free text and a day range live in the URL. Each entry expands to a Field / Before / After table the console computes from the before and after snapshots, plus an "Open record" deep link when the target page exists and is permitted.

1. Append-only: no create, update or delete route; entries are never edited (manifest CRUD /admin/audit-logs ops LS).
2. Every admin mutation writes one entry with actor type/id, action, entity type/id, before/after and the request IP (audit_logs columns; tables of each admin mutation row in the manifest; platform scenario manual: "every staff action is logged").
3. Passwords, TOTP secrets, token hashes, API key hashes and gateway secrets never enter before/after (manifest POST /admin/staff/:id/password: "never enters the log"); log only that a change happened.
4. System and worker actions log actorType system with actorId null and ip null (console reads null ip as "automatic", AuditDetails.tsx:45).
5. A suspended staff member keeps their name on old entries (map admin-team step 7).
6. The label of the record is captured at write time so later renames or deletions do not change history (frontend AuditLog JSDoc, types/index.ts:10-17).

Frontend mismatches with backend impact:

- **M188** The demo paged an in-memory list; the console pages GET /admin/audit-logs (25 per page) and appends on "Show more". Backend: Exact x-total-count and a stable newest-first order; the client dedupes by id.
- **M189** Entries have no names in the map; the console assumes joined actorName and entityLabel and shows action as the demo verb. Backend: Send actorName, entityLabel (snapshot) and a readable action phrase.
- **M190** The demo stored a ready diff; the API has before/after snapshots and the console computes the changed fields. Backend: Store JSON snapshots (changed fields for updates); mask secrets.
- **M191** The map names no filters; the console sends actorType/actorId, entityType, q and a from/to day range. Backend: Accept those filters with inclusive days.
- **M192** No audit export route; the demo button is not ported. Backend: Any future export must be permission-checked and audited.
- **M193** Open record links only to order, merchant, customer, supplier, service, blocklist, refund, dispute and staff. Backend: entityId must be the record's numeric id (0 when there is none).
- **M194** The IP shows in the expanded details; null reads "automatic". Backend: ip null for system entries.

## system

The sidebar footer polls GET /health every 60 s (only while the tab is visible, no retry) and shows "API healthy", "API degraded" with the failing dependencies, or "API unreachable". Any non-2xx answer, non-JSON body, network or CORS failure reads as unreachable.

1. Public route on the system surface; reports Postgres and Redis (manifest GET /health).
2. Answers JSON (a non-JSON 2xx becomes INVALID_RESPONSE in the client and reads as unreachable, client.ts:100-111).
3. Same CORS policy as /admin: exact console origin + credentials (the client always sends credentials:include).
4. Must not leak internals (versions, hostnames, stack traces).

Frontend mismatches with backend impact:

- **M9** The demo footer says the data is synthetic; the console footer shows API health from GET /health instead. Backend: GET /health is polled every 60 s from every open console tab with credentials: keep it cheap, JSON, CORS-enabled.
- **M201** The maintenance banner reads GET /admin/system/health and only staff with system:read see it; question whether me or /health should carry it. Backend: No change required now; see questions (auth 7, system 3).

## orders

The Orders page (/orders) is the staff queue for B2B and B2C orders: a server-paged list with tabs (Open, Needs review, Queued, Processing, Completed, Rejected, All), toolbar filters, per-tab counts read from x-total-count, a CSV export and a drawer per order (detail, timeline, ledger trail, pricing snapshot). The drawer and bulk bar run every order action (accept, reply, reject, reopen, refund, verification, notes, dispatch, fetch, change-supplier) and the paste-based bulk reply. The same list is embedded on merchant/customer pages (fixed clientId/customerId), in the command palette and in the supplier reroute dialog.

1. Status = map Dhru codes pending 0, processing 1, completed 4, rejected 3 (orders slice statuses). Open = pending|processing (status.ts:14-16); state-changing actions on a closed order answer 409 ORDER_NOT_OPEN (mock ordersShared.ts:13-14), so double clicks are harmless (no Idempotency-Key is sent).
2. queue derivation (mock src/mocks/orders.ts:110-138, map scenarios manual/timeout): review = B2C order held by risk (dispatch_state held, risk_assessments review undecided); manual = status pending and dispatch_state manual (manual step 5); needs_attention = dispatch_state needs_attention (timeout step 8; status stays pending until a REFERENCEID, the mock uses processing, the UI renders both); verification = status completed and verification_status requested; pending = status pending and dispatch_state pending (waiting in the outbox); otherwise null. After accept the queue must become null although no supplier is involved.
3. reviewReason is readable text per queue: manual 'Manual service: operator dispatch required' (src/mocks/orders.ts:59), verification 'The merchant asked for the result to be checked', needs_attention = the supplier error or timeout text, review = risk summary; stored in the review order_event data.reason.
4. pastSla=true (demo isBreach 11-state.js:64, mock handlers/orders.ts:19-22): open, not in a review queue (manual, needs_attention, verification, review), and now - created_at > the service's SLA minutes.
5. Ledger per action (map moneyEvents): placement = order (client_wallet to client_hold) or b2c_pay; reply = complete (cogs leg only when a supplier executed the order) or b2c_deliver; reject = reject or b2c_refund; refund = revenue to client_wallet (cogs kept); reopen = revenue back to client_hold/customer_funds; verification refund = refund; accept, notes, change-supplier, dispatch and an unfinished fetch move no money. Each posting goes through postTransaction with ref_type order, ref_id = order id and one idempotency key per transition (decision 024); the drawer reads GET /admin/ledger/transactions?refType=order&refId=<id> sorted createdAt asc (useLedgerTrail.ts:12-13); mock tx kinds order_settle, order_release, refund, adjustment (orders.test.ts:157-189).
6. Every staff action writes order_events and audit_logs (map manual step 8); every status change emits outbox order.status_changed with the whole order (EVENT row).
7. Supplier timeout: no automatic resend; the order waits in needs_attention with the balance still held (map timeout step 8, decision 020). The UI recommends Fetch when supplier_ref exists, else Retry (lib/actions.ts:44-71).
8. Refund route only for completed B2B orders; B2C is refunded via /admin/refunds (map row, M25). Reopen and refund need orders:reopen; other actions orders:update (map).
9. Held B2C orders (queue review) are decided only through POST /admin/risk/orders/:id/approve|refund (risk:decide, M28); the UI offers no order action on them, the server should refuse reply/reject/dispatch with 409 (proposal ORDER_HELD).
10. Inventory-backed services: reserve a code at placement (inventory_codes.status reserved, order_id), mark it sold on completion (result_code = the code), release it to available when the order is rejected before delivery; a delivered code never returns to stock (refund/reopen leave it sold).
11. A service with no active supplier link, or executionMode manual, puts new orders in the manual queue (dispatch_state manual) (useReplaceLinks.ts:29-31, map manual scenario).
12. Field lengths the server must accept: reject reason 120, reopen reason 140, note 500, reply comment 200, verification note 140 (component maxLength attributes).
13. orders.source values dhru | v1 | portal | store | admin (status.ts:129-138); service types lower case imei|server|remote|file (M21).
14. Register GET /admin/orders/export (and other static sub-routes) before GET /admin/orders/:id (handlers/orders.ts:1-3).

## services

The Services & pricing page (/services) manages the catalog: a server-paged services table with filters and below-floor chips, create/edit/delete, price and switch edits, replace-all dialogs for custom fields, option lists and group prices, and a bulk price change (preview, then apply). Other tabs: Categories (CRUD), Rules and groups (pricing rules CRUD plus the floor policy), Price resolver (server-resolved price with steps for one merchant) and Code inventory (masked code list, import, void). It also reads the merchants feature's client groups and clients as private lookups.

1. Floor = cost + minProfit; minProfit = the service's own min_profit when set, else a matching pricing rule's min_profit (> 0), else max(round(6% x cost, 2), 0.02) (demo 10-data.js:215, FloorPolicy.tsx:8-10). A PATCH basePrice under the floor is refused with 422 on basePrice (demo setPrice, serviceRoutes.ts:145-155); orders always pay max(resolved price, floor) with clamped=true (map: selling below the minimum price is blocked).
2. Bulk price apply saves prices under the floor and reports their count (useBulkPrice.ts:25-29); the floor is still enforced at order time.
3. Resolver order (demo resolveWith, mock pricing.ts:63-141): client override (service_client_prices) wins; else group service price (service_group_prices); else base price, then the category rule (active, scope category, target = the service's category, group null or the merchant's group, lowest priority number), then the group discount (client_groups.discount_percent); then the floor clamp. A fixed price (client or group) skips the rule and the discount.
4. Rule direction comes from kind: margin adds, discount and promo subtract; percent and fixed are >= 0 with at least one > 0 (ruleRoutes.ts:46-75); a promo applies only between startsAt and endsAt; rule changes affect new orders only.
5. Categories: allowed_group_ids empty = visible to every group (M94); no parent category; category type is one of the four service types.
6. Delete guards: category with services 409 CATEGORY_IN_USE; service with orders 409 SERVICE_IN_USE ('Disable it instead'); rules delete freely.
7. Service code is unique case-insensitive: 409 CODE_TAKEN with errors[{field: code}] on create and edit.
8. Replace-all PUTs (fields, options, group-prices) delete and insert in one transaction and answer the saved list in order.
9. Inventory: codes encrypted (code_enc), deduplicated globally on a keyed hash, never returned in clear or logged; the list shows the last four characters; void affects only available codes (reserved belong to open orders, sold were delivered).
10. A disabled service is hidden from merchants (imeiservicelist) while its open orders continue; executionMode manual sends new orders to the manual queue (types/service.ts ServiceStatus/ExecutionMode JSDoc, map manual scenario).
11. Money maths in decimal: prices rounded half-up to 2 decimals at the named points (mock round), emitted as 4-dp strings (decision 011); marginPct and percent are decimal strings.
12. Lookups read by these screens (merchants feature routes, no @route here): GET /admin/client-groups?_start=0&_end=200&_sort=sort&_order=asc (groups:read; rows need kind incl. b2c_retail and discountPercent, optional merchantCount) and GET /admin/clients?_start=0&_end=200&_sort=name&_order=asc (clients:read; optional group join) (api/lookups.ts).
13. Every catalog and pricing write is audit-logged (map: any admin mutation goes to audit_logs).
14. Register POST /admin/services/bulk-price/* (and GET /admin/pricing/resolve) so they never fall into /admin/services/:id handlers (mocks/index.ts:16-17).

Frontend mismatches with backend impact:

- **M91** Rows carry code, slaMinutes, minProfit, costChangedFrom, executionMode and category/supplier joins that services lacks. Backend: New columns (code, sla_minutes, min_profit, cost_was) and joins from links.

## suppliers

The Suppliers page (/suppliers) lists every supplier with server-computed health, success rates, latency, open-order counts and balance runway, and shows a detail with 24 hourly points, connection settings, the services linked to it and a live API log polled every 10 s. Actions: connect, edit connection, disable/enable, delete, test connection, sync now, import services (pick from the supplier catalogue, preview, import), edit a service's supplier chain, reroute open orders (via the orders routes) and a 7-day spend/rejection/speed line from the supplier report. System health pauses/resumes suppliers through the same PATCH.

1. suppliers.status is active | disabled | paused (M60, M197; scenario system-alert steps 8 and 11). Only active takes new orders (state.ts:21-23); paused or disabled makes routing skip to the next link by priority while open orders stay (system-alert step 8); Enable (status active) resumes both.
2. health up | degraded | down is computed by the server (service_checks plus supplier_api_logs error/timeout rate, circuit breaker); the console only words it; reroute targets are active and not down (state.ts:37-39, RetryMenu.tsx:30-37).
3. lowBalance = balance < low_balance_alert or runway under 2 days (demo rule, M65); runwayDays = balance / (supplier cost of the last 7 days / 7), null with no spend.
4. The API key is write-only: stored encrypted (api_key_enc), never returned; apiKeyHint = first 5 characters kept at write (handlers.ts:54); an omitted key on edit keeps the stored one (M68).
5. Every supplier call (dispatch, poll, test, sync) writes supplier_api_logs with masked request/response; order_id is null for test and sync.
6. Delete only when no order references the supplier and no service links it; otherwise 409 SUPPLIER_IN_USE (Disable instead).
7. Sync touches supplier_services and suppliers only; services.cost changes through import of changed items, with the old cost kept for costChangedFrom.
8. A service whose chain is empty (or has no active supplier) sends new orders to the manual queue; dispatch uses the first active link by priority.
9. Reroute (M62) uses the orders routes: GET /admin/orders?supplierId=<id>&status=pending&status=processing&_sort=createdAt&_order=asc&_start=0&_end=200, then change-supplier { supplierId, resetReference: true } and dispatch per order, sequentially; a 401 stops the run (lib/reroute.ts:18-40).
10. Amounts are shown with $: balance is in the supplier's currency as reported by accountinfo; costs are converted to USD with credit_rate.
11. Permissions (map): import and preview catalog:create; supplier-links catalog:update; report reports:read; logs and supplier services suppliers:read; test and sync suppliers:update; CRUD suppliers:* (M7).
12. Validation the UI relies on: name at least 2 chars and unique (case-insensitive), baseUrl http(s) with a host, apiKey required on create (handlers.ts:18-39); field names as in SUPPLIER_FIELDS (input.ts:21-32).

Frontend mismatches with backend impact:

- **M37** No route records a supplier top-up; balances come from sync. Backend: Balance only from accountinfo (test/sync); no top-up endpoint.

## system-health

The System health page (/system-health; no demo page, docs/system-health-design.md) shows a server-computed verdict, a six-tile KPI row and seven tabs (Overview, API, Orders & suppliers, Queues & jobs, Alerts & incidents, Data stores, Integrity) over the 30 routes of map group health; the app shell shows a maintenance banner from the same health read. Every figure is a server-judged Measure; the console only polls (15 s / 30 s / 5 s while a run is going) and runs operator actions (maintenance, queue retry/pause, run job, integrity run, ack, rule CRUD/mute, incident declare/update/close) through confirm dialogs that show the server's problem+json. File paths without src/ are under src/features/system-health/.

1. The server judges every number: each figure is a Measure whose state comes from server-side thresholds; warn/crit are the limits applied, direction says which side is bad, value null => state unknown. The console never compares (types/common.ts:23-34; mocks/thresholds.ts:45-72).
2. No data is never healthy: while Prometheus is unavailable health is never 'operational' (map scenario system-alert step 5; M216); a figure without data is 'unknown', never 'ok' (mocks/thresholds.ts:45-47).
3. Overall status: 'outage' when a core component is down, 'degraded' when any component is down or degraded or a critical alert is open, else 'operational' (mocks/facts.ts:172-177).
4. A worker checks every minute: database, cache, storage, payment gateways and every supplier (accountinfo), writing status and latency to service_checks; uptime and outages derive from those rows, which are deleted after 90 days (scenario system-alert step 1; table service_checks).
5. Rules are evaluated every minute over their window; a breach creates one alert_events row (firing, severity, value, subject) unless the rule is muted (muted_until in the future) or switched off; e.g. supplier timeout rate > 20 % for 3 min -> critical alert on that supplier (scenario system-alert step 3; mocks/seedRules.ts).
6. Notifications: one message per rule channel (telegram, email), repeated only after the reminder interval until acknowledged (scenario system-alert step 4).
7. Acknowledge moves firing -> acknowledged only, records acknowledged_by/at + audit_logs and stops reminders; the alert stays open and an acknowledged critical alert still counts as critical (step 6; M214); otherwise 409 ALERT_ACKNOWLEDGED / ALERT_RESOLVED (mocks/routes/alerts.ts:35-51).
8. Only the server resolves alerts: after 3 consecutive ok minutes (resolved_at + a 'resolved' message); an acknowledged alert never closes earlier (step 10). There is no resolve endpoint.
9. Incidents: declaring starts the timeline at 'investigating' and links the alert (step 7); one incident per alert (mocks/routes/incidents.ts:53-58); every status change or update adds a server-written timeline line; closing needs rootCause (10+) and the optional update is the action taken (step 11; M205); a resolved incident is a record -> any PATCH 409 INCIDENT_CLOSED; incidents are never deleted (map ops LSCU).
10. Supplier pause (PATCH /admin/suppliers/:id status=paused) routes new orders to the next supplier by priority in service_supplier_links; orders already sent stay as they are (step 8); a paused supplier keeps its checks, a disabled one is unchecked (health 'unknown') (mocks/facts.ts:104-128).
11. Maintenance: the chosen scope answers 503 MAINTENANCE with the message and expected end; checkout maintenance creates no checkout session and holds nothing; the admin console and running merchant orders keep working; on/off/change are audited with the staff member; only PUT {enabled:false} ends it (scenario system-integrity steps 4, 5, 8; manifest PUT /admin/system/maintenance).
12. Ledger integrity: the nightly ledger_integrity job runs four read-only checks (entries sum to zero, account balance = sum of its lines, holds stuck > 24 h, confirmed payments without an entry) and stores the result in job_runs.result; a difference fires the critical ledger_mismatch rule naming the account and difference; corrections are reversing entries (POST /admin/clients/:id/wallet/adjust), never edits; a clean manual run resolves the alert (scenario system-integrity steps 1-3, 6-7).
13. Every scheduled or manual run writes job_runs (trigger schedule|manual|event; triggered_by for manual) (D020; manifest POST /admin/system/jobs/:name/run); one run per job at a time -> 409 JOB_ALREADY_RUNNING (mocks/routes/queues.ts:109-116, mocks/routes/integrity.ts:19-27); proposal: a reaper fails runs stuck in 'running' past a timeout so the guard cannot block forever.
14. Queue actions: pausing needs a reason (3+ chars) kept in audit_logs (M204); retry touches failed jobs only and answers how many moved (mocks/routes/queues.ts:34-87).
15. Every write of the group writes audit_logs with the staff member (manifest tables of every health write).
16. Permissions (manifest): system:read for every /admin/system read; system:manage for maintenance, retry, pause, run job and integrity run; alerts:read for alerts and rules, alerts:create/update/delete for rules, alerts:update for ack; incidents:read/create/update; suppliers:update for pause/resume. 403 detail names the missing permission (mocks/http.ts:44-46). Default roles: Owner and Admin manage; Finance, Support, Risk reviewer and Read only view (M198).
17. Database outage: reads that need live Postgres rows answer 503 DATABASE_UNAVAILABLE (mock: orders-health, integrity, integrity run; mocks/profile.ts:94), while health keeps answering from the snapshot and /database answers 200 status 'down' (M212).
18. Component keys are stable ids: fixed core keys incl. 'workers', plus 'supplier:<id>' and 'gateway:<id>'; incident components are validated against the known keys (422 'Unknown component', mocks/routes/incidents.ts:42-51); the declare prefill maps supplier alerts to 'supplier:<subjectId>' and queue alerts to 'workers' (tabs/alerts/incidents.ts:82-83).
19. Seed the rules the map scenarios need: supplier_timeout_rate (gt 20, 180 s, critical) and ledger_mismatch (gt 0, critical); the mock seeds ten rules with defaults worth copying (mocks/seedRules.ts).
20. Range: tabs send range=1h|6h|24h|7d (default 24h); the KPI row always reads metrics?range=24h, queues, orders-health and health (30-day uptime) whatever the page range (header/useKpis.ts:53-58; ASSUMED_CONTRACTS 'Health summary details').
21. Polling: health, alerts and queues every 15 s; other cards every 30 s; jobs and integrity every 5 s while a run is going; hidden tabs pause, focus refetches, answers younger than 5 s are reused, 5xx GETs are retried once (hooks/keys.ts:47; hooks/useHealthQuery.ts:26-45; src/lib/query/useApiQuery.ts:26-28). Serve health from a per-minute snapshot and checks/metrics/errors/database from ~15-30 s caches keyed by params.
