# 074: the code of a service is made by the server, and a shop switch that changes nothing writes no audit row

Status: accepted, 2026-11-27 (the owner's order of that day: "in the Code field of a service I want the code generated by the system"; the
owner accepted the lead's format). Builds on decisions 060 (the Catalog page), 069 (own cost) and 073 (an IMEI service's default field). The
console and the shop record their own side of the change.

**Context.** A service made by hand had a code that staff typed (typed codes of any shape, some with spaces or punctuation); a service
brought in by a supplier import already gets one by itself (`IMP-<supplier service id>`, then `-2`, `-3`, ...). The owner does not want
to invent codes. Separately, production's audit log holds rows "unlisted from storefront" whose `before` and `after` are both
`{ "isListed": false }`: the console once sent the same shop switch five times, and the route wrote a row for each.

## Part 1: `POST /admin/services` makes the code

- **`code` is optional in the request.** Sent, it is judged exactly as before (trimmed, 1 to 40 characters, `409 CODE_TAKEN` on `code` when
  a live service holds it, ignoring case). Left out, the server makes it. A blank code (`"   "`) is still `422` on `code`.
- **Format: `<PREFIX>-<id>`, the new service's own id.** Prefix by type: `imei` is `IMEI`, `server` is `SRV`, `remote` is `RMT`, `file` is
  `FILE` (`SERVICE_CODE_PREFIX`, `madeServiceCode` in `src/modules/catalog/domain/service-code.ts`). Example: `IMEI-1042`. The prefixes differ
  from the importer's `IMP`, so the two families never read alike.
- **When a live service already holds that code** (ignoring case: someone typed it by hand earlier), the server takes `<PREFIX>-<id>-2`,
  `-3`, ... : the same helper the import uses (`firstFreeServiceCode`, `src/modules/catalog/application/service-code.ts`; the import's private
  `freeCode` moved there). An archived service gives its code back, as everywhere.
- **One transaction, one write, no placeholder.** The id column is `GENERATED ALWAYS AS IDENTITY`, so the create first takes the id from the
  sequence (`reserveServiceId`: `nextval(pg_get_serial_sequence('public.services', 'id'))`, the pattern of `invoices` and `support_tickets`),
  works out the code from it and inserts the row once under that id (`insertServiceRowWithId`, `OVERRIDING SYSTEM VALUE`). The stored row, the
  answer and the audit row `created service` all carry the final code; nothing outside the transaction ever sees a placeholder. A create that
  is refused after the id was taken (the floor check of decision 069, a lost race on a typed code) rolls back: the id is only a gap in the
  numbers.
- **Two creates at the same moment both succeed.** Each takes its own id from the sequence (it never hands out one twice), so each makes a
  different base code (`IMEI-7`, `IMEI-8`); a suffixed code (`IMEI-7-2`) can only come from service 7, so two made codes never collide. Only a
  code typed by hand can be in the way. The unique index `services_code_uq` (`lower(code)` among live services) remains the last guard: the one
  window left is a hand-typed code that commits between the free-code read and the insert, and that answers `409 CODE_TAKEN` (never 500) on
  `code`, as the same race on a typed code always did. Tested with six simultaneous creates.
- **`PATCH /admin/services/:id` is unchanged**: it still accepts `code` (the console simply stops sending it). **No migration, and no existing
  code changes**: the typed codes in production stay as they are.
- **Release order: this backend before the console that stops sending `code`.** Until then the console keeps sending a typed code, which is
  still judged as before; the other order would send a create without `code` to a backend that refuses it (`422`).

## Part 2: a shop switch that changes nothing writes nothing

`PATCH /admin/service-listings/:id` with `isListed` equal to the value the listing already holds, read **under the service and listing locks**
(not the earlier unlocked read), writes nothing for the switch: no audit row `listed on storefront` or `unlisted from storefront`, no
`listed_at`, no `is_listed` write. The answer is still `200` with the listing. Every other key of the same request is handled as before, and
each real change keeps its own row (`changed retail price of`, `edited listing of`). The permission checks and the refusals
(`SERVICE_DISABLED`, `LISTING_LOCKED`, `storefront:publish` for a real switch-on, `pricing:update` for a price key) are decided exactly as before:
only the writes of the no-op switch go. The search signal (`storefront.listing_changed`) is written only when something was written (the
switch, the retail price or the content of the same request); a request that holds nothing but a no-op switch writes none. (The publish
run's own switch, `publish-switch.ts`, already counted such a listing as `unchanged`.)

**What this needed in the audit enforcement.** The audit enforcement (decision 018) fails a staff write that wrote no audit row (a `500` in
development and tests, an error log in production). A request that changes nothing is a legitimate write of no row, so a use case may now say
so: `AuditService.nothingChanged()` marks the request (`markNothingToAudit`, `RequestContext.auditNothingToWrite`) and the enforcement lets it
pass. It is for a use case that decided nothing at all changed; any use case that writes something must still call `AuditService.record`. The
listing route is the only caller. The alternative, `audit: false` on the whole route, was rejected: it would switch the safety net off for the
price and content writes of the same route.

## Consequences

- Staff never type a code for a new service; the console shows it read only. Old codes (typed, `IMP-`) are untouched and can still be
  changed by hand with `PATCH`.
- The audit log of production keeps its old duplicate rows (an append-only table); no new ones appear.
- Not changed: the cache, the queues, the migrations, the importer's `IMP-` codes (only the helper behind them moved).
